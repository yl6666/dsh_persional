# 多仓协同开发插件 · 产品设计（v0.5 初稿）

> 状态：设计稿，待方向校正后迭代。本文档随仓库一起维护。
> 目标平台：DeepSeek Harness（DSH）插件。

---

## 1. 一句话定位

**一次下发一个跨仓需求，系统自动分析多仓之间的关系，拆解出每个仓的修改方案并自动执行修改，最终每个仓库产出独立、可审核的提交。**

关键词：**一次下发 · 关系分析 · 方案先行 · 自动修改 · 一会话一仓**。

---

## 2. 要解决的真实问题

- 一个需求横跨多个仓库（前端 + 后端 + 公共库 / 微服务 / multi-repo），人工要在多个仓之间来回切换、手工维护依赖顺序。
- 改一个仓的对外契约（API / 事件 / 表结构）时，**不知道下游谁会被打破**，靠人肉排查。
- 多个仓并行修改时，容易出现写路径重叠、版本不一致、发布顺序错乱。
- 传统「一对一 agent 会话」视角局限在单个仓库，**看不到跨仓关系的全局后果**。

本插件把「跨仓关系」提升为一等公民，让一次下发、多仓协同变成可落地产品。

---

## 3. 总体架构（四层）

```
┌─────────────────────────────────────────────────────────────┐
│  L4 看板 UI        —— 需求入口 + 关系图谱可视化 + 方案审阅 + 进度 │
├─────────────────────────────────────────────────────────────┤
│  L3 编排层         —— 需求澄清 → 需求解构 → 影响面 → 方案 → 调度执行 │
│                        （一次下发的完整管道）                    │
├─────────────────────────────────────────────────────────────┤
│  L2 关系图谱层  ★核心   —— RepoGraph：多仓关系的建模/抽取/计算/校正│
├─────────────────────────────────────────────────────────────┤
│  L1 执行层        —— 一会话一仓 + 隔离 workspace + 协同原语 + git │
└─────────────────────────────────────────────────────────────┘
```

- **L2 关系图谱层是整个产品的地基和大脑**：它不只在「影响面分析」那一刻被用到，而是贯穿需求解构、方案生成、执行编排、变更广播、发布排序、图谱反馈的全链路。
- **L1 执行层大量复用 DSH 现成能力**（见 §8），是本产品风险最低的一层。
- **L3 编排层是我们自研的核心**：把「关系 + 需求 + 方案 + 并行执行」串成一条流水线。
- **L4 是用户体验的落点**：一张会动的看板，不是静态列表。

## 4. ★ 核心功能：多仓关系图谱（RepoGraph）

> 这是最核心的功能。设计原则：**先确定性、后概率性；先静态、后语义；LLM 只补机器读不出的那层，且永远可人工校正。**

### 4.1 四层关系模型（边的分类）

| 层级 | 关系类型 | 确定性 | 来源 | 抽取方式 |
|---|---|---|---|---|
| **L1** | **构建/包管理依赖**（build） | 高，机器确定 | `package.json`、`pnpm-workspace.yaml`、`go.mod`、`Cargo.toml`、`requirements.txt`/`pyproject.toml`、`pom.xml`/`build.gradle`、`Gemfile`、`composer.json` | 纯文本解析，零 LLM |
| **L2** | **源码引用依赖**（code） | 中高 | 跨仓 `import/require/use`、通过包导入路径 | tree-sitter / LSP（借力 DSH lsp，需评估跨仓多根支持）+ 包名→仓映射 |
| **L3** | **契约/接口依赖**（contract）★ | 中高 | OpenAPI/Swagger、protobuf、GraphQL schema、Avro、共享 JSON Schema、RPC 定义、事件 schema、DB schema/migration | 静态定位契约文件 + LLM 归纳契约内容与消费方 |
| **L4** | **隐式/语义依赖**（semantic） | 中低，带置信度 | README、架构文档、约定俗成的调用、共享基础设施、发布顺序约定 | LLM 语义标注 |

- **L3 契约依赖是跨仓协同的核心**：L1/L2 告诉我「谁链接了谁」，L3 告诉我「谁依赖了谁对外暴露的什么」，这是「改 A 会不会破 B」的关键。
- **L4 是兜底**：manifest 和代码读不出的隐性关系（如约定发布顺序、共享缓存 key），靠 LLM 补齐，并强制带置信度。

### 4.2 图谱数据模型

**节点（RepoNode）**

```
RepoNode {
  id / name / path / remote
  职责标签[]        // 如 order-service、鉴权、公共 SDK —— LLM 生成，可人工改
  技术栈 / 语言 / 构建系统
  指纹 fingerprint  // = 关键文件（manifest + 契约）内容 hash，驱动增量重扫
}
```

**边（RepoEdge）**

```
RepoEdge {
  from → to         // 方向约定：from 依赖 to（from=下游消费方，to=上游提供方）
  type: build | code | contract | semantic
  contractRef?     // 具体契约引用：端点 / 方法 / 事件 topic / 表 / schema
  strength         // 置信度 / 强度
  versionConstraint? // 版本约束（如 >=1.2）
}
```

**派生视图（从图实时计算，不单独持久化）**

- **影响面 blast radius** = 反向可达集：改 A → 谁会被波及。
- **依赖链** = 正向可达集：A 依赖谁。
- **拓扑序**：修改/发布的先后顺序（对有向图做拓扑排序）。
- **契约影响面**：改 A 的契约 X → 哪些仓消费了 X（精确到契约粒度，而非仓粒度）。
- **写范围重叠**：多个仓的 `writeScopes` 相交时给出冲突预警。

### 4.3 三级抽取器

```
manifest-extractor   纯函数，解析各类构建文件 → build 边。秒级、无 LLM、可缓存、可回归测试。
contract-extractor   定位 OAS/proto/GraphQL/schema/migration 等契约文件，
                     提取「契约名 + 提供方 + 消费方」。消费方靠静态引用 + 包名映射。
semantic-annotator   LLM：读 README/架构文档/代码摘要 → 职责标签 + 隐式边 + 置信度。
                     输出结构化 JSON（可走 subagent 让模型做标注）。
```

### 4.4 增量与缓存

- 每个仓维护**指纹**（manifest + 契约文件内容 hash）；**只有指纹变化才重扫该仓**，图增量更新，绝不全量重扫。
- 图谱持久化为**项目级文件**（版本化、可 diff、可回放），随 DSH 会话一起可追溯。
- 目标：秒级回答「改 A 会波及谁」，而不是每次现场分析。

### 4.5 人机协同（关键设计）

- 图谱是**活的资产，不是一次性扫描结果**：人能在看板上补边 / 删边 / 改标签 / 修置信度。
- 执行产生的实际变更、契约漂移、下游反馈 → **回写图谱**（新增边、标记噪声边、上调/下调置信度）。
- 效果：**越用越准**。第一次可能要人校一版，之后越来越不需要。
- 交互载体：这套校正通过**图形化关系编辑器**（见 §7.1）完成——拖拽连线、改标签、补契约，而非改 JSON。

## 5. ★ 核心功能：一次下发全链路

> 用户最终目的：**需求下发一次 → 生成对应仓的修改方案 → 修改**。关系图在此全程驱动。

### 5.1 完整管道（8 步）

```
需求(自然语言)
   │
   ▼
[0] 需求澄清 (按需触发)  ★新增
   │  需求简单/模糊 → 基于图谱针对性追问，补齐关键信息
   │  信息充分则跳过此步，直接进入解构
   │
   ▼
[1] 需求解构 (LLM + 图谱)
   │  用 RepoGraph 的职责标签 + 图结构，把需求映射到「相关仓集合 + 每仓意图」
   │  产出：涉及仓候选 + 每仓任务假设
   │
   ▼
[2] 影响面分析 (图算法 + LLM)  ★关系图主场
   │  对候选仓求反向可达集 → 补出「被波及仓」
   │  计算拓扑序 → 依赖顺序
   │  检测写范围重叠 → 冲突点
   │  定位契约变更点 → 需协调的上游→下游边
   │
   ▼
[3] 方案生成 (每仓一份结构化方案)  ★方案先行
   │  给每个仓生成《修改方案》：改动点 / 契约变更 / 下游影响 / 验收标准
   │
   ▼
[4] 方案评审 (人审闸门，可跳过/可分级)
   │  重点审「契约变更 + 跨仓影响」这条边，而非逐行审代码
   │
   ▼
[5] 编排执行 (拓扑序并行)  ★一会话一仓
   │  按依赖顺序调度：上游先改 → 契约变更广播 → 下游解锁适配
   │  每仓一个隔离会话 + 独立 workspace
   │
   ▼
[6] 提交与合并 (每仓原子)
   │  每仓独立 commit/push/PR；发布顺序 = 反向拓扑
   │
   ▼
[7] 图谱反馈 (持续校正)
       执行结果 + 实际变更 + 契约漂移 → 回写 RepoGraph
```

### 5.2 ★ 需求澄清与追问（Clarification）

> 回答「需求描述简单时怎么办」——不盲目开工，先按实际情况针对性追问/补充，补齐后再继续。

**定位**：一次下发管道里的「需求质量闸门」。信息不足时拦住，问清楚再走；信息充分时直接跳过，不添负担。

**触发条件（什么时候追问）**

- 目标仓不明确：需求没说涉及哪些仓/服务，而图谱里有多个候选。
- 改动边界模糊：新增 / 改行为 / 修 bug 不明，影响范围不清。
- 契约变更未定：跨仓契约（API / 事件 / 表）怎么变、是否允许破坏性变更、要不要兼容。
- 验收标准缺失：什么叫「做完」、测试要求、是否上线。
- 歧义或矛盾：需求自相矛盾，或提到图谱里不存在的仓/服务（异常态）。

**追问的原则（关键：避免变成烦人的挤牙膏）**

1. **只问关键、问得准**：只问「会影响方案正确性 / 执行安全」的信息，其余给默认值。
2. **一次尽量问全**：把缺口打包成一批结构化问题，不零散反复问。
3. **基于图谱追问**：带着关系分析的推断问，而不是空泛地「请补充需求」。
4. **分级**：阻断级（不答无法继续）必问；可默认级（有合理默认）给默认，用户可改或跳过。

**追问形态（复用 DSH 提问机制）**

- 结构化选择：单选/多选 + 推荐项 + 每项的 tradeoff 说明。
- 开放式补充：需要自由输入的（如新 API 字段定义）。
- 带默认确认：给出系统推断的默认方案，用户确认或改。

**示例（基于图谱的追问）**

> 需求：「订单超时自动取消」
> 图谱推断：涉及 order-service（取消逻辑）、notify-service（通知），两者共享事件契约 `order.cancelled`。
> 追问：① `order.cancelled` 事件字段是否新增「取消原因」？② 是否要求 30 天内兼容旧订阅方（下游除 notify-service 外还有 audit-service）？③ 取消后的通知渠道是 push / 邮件 / 两者？

**产物与追溯**

- 澄清结果合并为「完整需求规格」：原始需求 + 补充决策（结构化）。
- 决策持久化、可追溯，作为后续方案与执行的事实依据。
- 支持「跳过 / 按默认 / 我自己补充」三种响应。

**技术落点**

- 复用 DSH 的 ask / approval 机制（`ctx.approval` 应答器 + 面向模型的提问工具，DSH 已内置 AskUserQuestion 类能力）。
- 「缺口识别 + 问题生成」由 LLM 完成，图谱供给上下文与异常检测。

### 5.3 结构化修改方案（RepoModificationPlan）

「生成对应仓的修改方案」必须结构化，让人能审「契约边界」而不是海量 diff：

```
RepoModificationPlan {
  repo
  变更摘要
  改动点[]                // 文件/模块/函数级
  契约影响 {
    破坏性变更[]          // 改了什么对外契约
    下游受影响的仓[]      // 从图反查，精确到契约
  }
  依赖的前提[]            // 需上游先完成什么
  验收标准[]
}
```

- 这套结构化方案的护城河：**单仓 agent 看不到契约破坏的全局后果，而我们有图**。
- 人审的是高风险「契约边界」，而非逐行代码，大幅降低评审负担。

## 6. 执行层：一会话一仓 + 协同

- **强隔离**：每仓一个会话 + 独立 workspace（`cwd` 绑定），AGENTS.md / 工具作用域 / 文件沙箱按仓隔离；上下文不串味、省 token、防跨仓幻觉。
- **可继续**：每仓会话持久化，可冷恢复，中断不丢状态。
- **协同原语**：复用 DSH 的 roster / task DAG（`blockedBy` 依赖 + `writeScopes` 冲突检测）/ 持久 mailbox（去重、可恢复）。
- **git 生命周期**：每仓独立 commit / push / PR，原子、可单独 review。

## 7. 看板 UI（体验落点）

看板 = 需求入口 + 关系图谱可视化 + 方案审阅 + 进度卡；其中关系图谱同时承载「看」与「编辑」两种形态。

- **需求入口**：一句话/一段需求下发。
- **关系图谱可视化**：节点=仓、边=关系（分颜色/类型），高亮影响面与拓扑序、写冲突红标。
- **★ 关系图谱编辑器**：图形化「组合」多仓关系（见 §7.1）。
- **方案审阅**：每仓一份结构化方案，重点标注契约变更点。
- **进度卡**：每仓实时状态（running / idle / inactive）、dirty 状态、最近提交、diff 摘要。

### 7.1 ★ 图形化关系编辑器（Graph Editor）

> 回答「能不能用图形化 UI 组合多仓关系」——能，而且这是本产品与纯自动分析工具拉开差距的关键交互。

**定位**：RepoGraph 的「人工构建 + 校正」前端。自动分析产出「底图」，编辑器负责「人工真相」——两者双向同步、合并收敛。

**为什么要图形化（三个刚需）**

1. **冷启动**：新项目自动分析不全面（尤其隐式依赖、跨团队约定），人可以先把关系骨架「画」出来。
2. **校正**：把「改 JSON / 列表」升级为「拖拽连线」的直观体验。
3. **组合**：用户说的「组合多仓关系」——选仓 + 连线 + 定关系，一键成图。

**交互形态（三栏）**

- 左栏 · 仓库库：可搜索的仓库 / workspace 列表，支持「新增仓库」（clone URL 或本地路径），拖入画布即成节点。
- 中栏 · 画布：节点=仓、边=关系（分型分色）；拖拽、缩放、自动布局、分组。
- 右栏 · 属性面板：选中节点/边后编辑——职责标签、关系类型、契约引用、置信度、版本约束。

**关键交互**

- 拖仓库进画布 → 生成节点；两个节点拖线 → 选关系类型（build/code/contract/semantic）+ 填契约引用。
- **一键自动补全**：对画布内的仓跑 manifest/contract 抽取器，自动补边，人再确认/删改。
- **影响面高亮**：选中一个节点，反向可达集着色；拓扑序分层；写冲突红标。
- 编辑结果**双向同步回 RepoGraph 持久化**。

**人机合并策略（关键，保证收敛不打架）**

| 来源 | 性质 | 规则 |
|---|---|---|
| 自动抽取的边 | 候选边（带置信度） | 可被人改/删 |
| 人工画的边 | 确认边（高置信度） | 自动分析**永不覆盖** |
| 人工删的边 | 否定标记 | 自动分析**不再重复建议** |

**技术落点**

- React 18 + TypeScript（DSH 前端栈已确认）。
- 复用 DSH UI：`dsh-client-ui-slots`（挂载点）、`dsh-client-ui-primitives`（基础组件）、`dsh-client-ui-dockkit`（面板/停靠）。
- 图画布：SVG/Canvas 自绘（可控、零依赖）起步；交互复杂再评估 react-flow / cytoscape.js（需评估包体积与沙箱兼容）。
- 接入方式：`dsh.client` 声明 + `exports["./client"]` 导出 bundle。

## 8. 与 DSH 现有能力的映射

| 能力 | DSH 入口 | 复用 vs 自研 | 备注 |
|---|---|---|---|

| 可继续子会话 | `ctx.subagents`（continuable） | **复用** | 每仓会话持久化/冷恢复 |
| 一会话一目录绑定 | `ctx.workspaceRegistry` + `SessionHeader.cwd` | **复用** | 「一会话一仓」结构上天然成立 |

| 人审闸门 | approval 子系统 | **复用** | 方案/契约/合并的审批 |
| 需求澄清/提问 | `ctx.approval` + 面向模型的 ask 工具 | **复用** | DSH 已内置提问/应答机制 |
| 静态解析（import/符号） | `dsh-lsp` | **借力（待评估）** | 需验证跨仓多根支持 |

| **RepoGraph 存储与计算** | 可借 DSH storage | **自研为主** | MVP 先项目级 JSON，后续评估 DSH 领域存储 |

## 9. 关键亮点汇总（重述）

1. **需求一次下发，方案先行**：自动拆解到 N 仓 + 生成结构化方案，人只审契约边界。
2. **★ 多仓关系图谱**：四层关系（build/code/contract/semantic），确定性 + 语义双驱动，可人工校正、越用越准。
3. **影响面分析**：动一仓自动算出波及谁、破哪些契约。
4. **拓扑编排 + 写冲突检测**：安全的并行度，依赖顺序可解释。
5. **契约变更广播**：上游一变自动同步下游适配。
6. **一会话一仓隔离 + 全链路可回放**。
7. **★ 图形化组合关系**：拖拽连线把多仓关系「画」出来，自动分析与人工编辑合并收敛、永不打架。
8. **★ 智能追问补全**：需求简单时基于图谱针对性追问，一次问全、分级给默认，不盲目开工。

- 不做跨语言的运行时调用拓扑（trace-level），先聚焦仓库/构建/契约关系。
- 不做多仓 diff 的自动合并冲突仲裁（超出范围，先报告 + 人审）。

## 12. 开放决策点（待拍板）

1. **图谱粒度**：一张图 = 一个项目/一组相关仓，还是全局所有仓一张图？（倾向：一组相关仓一张图）
2. **语义标注预算**：LLM 标注会消费 token，是否提供「仅静态」「静态+语义」分级开关 / 按仓重要性裁剪？
3. **执行层选型**：优先基于 `ctx.agentTeams` 还是 `ctx.subagents` continuable？（倾向：先 subagents 起步，验证协同语义后再评估 agentTeams）
4. **人审分级**：方案评审 / 契约变更评审 / 每次 push 评审，哪些默认开启？
5. **git 凭据**：复用本机 SSH/credential manager，还是插件内配 token？
6. **追问策略**：追问是「一次性问全」还是「随执行按需追问」？是否允许用户全局关闭追问（全自动模式）？
7. **分发渠道**：npm 发布（真一键，推荐）/ GitHub + `prepare` / tarball？是否需要 GitHub Action 自动发 npm 的流水线？

## 13. 设计细化：数据模型 · 算法语义 · 管道协议

> 本文档从「想清楚要什么」进入「怎么做」的过渡层：先把跨模块都要用的数据结构和语义约定钉死，`order-service` 之后的实现才有统一的契约。

### 13.1 RepoGraph 落盘格式（版本化 JSON）

图持久化为项目级文件，版本号随结构迁移递增；邻接关系用**边表**而非邻接矩阵，便于人工编辑和增量追问。

```jsonc
{
  "version": 1,
  "project": "acme-checkout",                 // 图所属的项目/仓组
  "updatedAt": "2026-01-01T00:00:00Z",
  "nodes": {
    "order-service": {                        // key = 稳定 id（远程 URL 或规范路径），非 name
      "name": "order-service",
      "path": "/workspaces/order-service",    // 本地 checkout 路径（未 clone 则缺省）
      "remote": "git@github.com:acme/order-service.git",
      "labels": ["订单", "核心域"],            // 职责标签（LLM 生成 / 人工改）
      "fingerprint": "sha256:…",              // manifest + 契约内容 hash，驱动增量重扫
      "meta": { "stack": ["go"], "build": "go.mod" }
    }
  },
  "edges": [
    {
      "id": "e_01",
      "from": "order-service",                // from 依赖 to（下游 → 上游）
      "to": "notify-service",
      "type": "contract",                     // build | code | contract | semantic
      "contractRef": {                        // 仅 contract 边携带
        "kind": "event",                      // event | api | table | schema | rpc | …
        "name": "order.cancelled",
        "schema": "…契约内容或指针…"
      },
      "strength": 0.9,                        // 置信度/强度
      "source": "manual",                     // auto（自动抽取）| manual（人工画）
      "status": "confirmed",                  // candidate（候选）| confirmed（确认）| suppressed（否定）
      "versionConstraint": ">=1.2"
    }
  ],
  "suppressed": [                             // 人工否定标记，自动分析不再重复建议
    { "from": "order-service", "to": "audit-service", "type": "contract", "reason": "已改走 HTTP" }
  ]
}
```

**关键决策**

- 节点 key 用**稳定 id**（远程 URL / 规范路径），不用 name——name 可重名、可改。
- `source` + `status` 三态直接落地 §7.1 的合并策略：`manual+confirmed` 永不覆盖，`suppressed` 永不复活。
- `fingerprint` 使图谱**秒级增量更新**，绝不全量重扫。

### 13.2 图算法语义（影响面 / 拓扑序 / 环 / 写冲突）

**方向约定（全文档唯一真源）**：边 `A → B` = **A 依赖 B**（A 是下游消费方，B 是上游提供方）。

**① 依赖链 / 影响面（可达性）**

- `依赖链 deps(A)` = 从 A 出发沿边正向可达集 = A 依赖的所有仓。
- `影响面 impact(A)` = 从 A 出发沿边**反向**可达集 = 依赖 A 的所有仓 = 「改 A 会波及谁」。
- 可按边类型加权分层：仅沿 `contract` 边 → **契约影响面**（标注「会破谁」）；沿 `build` 边 → 编译影响面。默认「影响面」取全类型并集，但汇报时按类型分组。

**② 拓扑序（修改/发布顺序）**

- 对「涉及仓集合」的导出子图做拓扑排序，**上游（被依赖者）在前**：若 `A → B`，则 B 排在 A 前。
- 修改顺序 = 发布顺序 = 该拓扑序（上游先定契约、先发布，下游再适配、再升级依赖）。
- 无依赖关系的仓可以并行。

**③ 环检测与处理（不能回避）**

- 用强连通分量（SCC）检测环。
- 处理策略分级：
  1. **默认**：把环内所有仓**收缩为一个「原子编排单元」**——不强行排序，作为一个批次同时改、一起评审、一起发布。
  2. **契约环**（A 依赖 B 的契约、B 也依赖 A 的契约）→ 标记**高风险**，强制进入人审闸门，不做自动原子化。
- 收缩后的图必为 DAG，再跑拓扑序。

**④ 写范围冲突（writeScopes 重叠）**

- 每个仓任务携带提示性 `writeScopes`（路径前缀集合）。
- 两个**并行**任务的 writeScopes 存在前缀重叠（相等、或一个是另一个的前缀）→ 判定冲突：
  1. 降级为串行；
  2. 或提示拆分任务；
  3. 冲突不可消解时转人审。
- 作用域仅是提示（不是锁），真正的写安全仍由文件沙箱兜底。

### 13.3 一次下发：管道数据流协议（各步骤交接契约）

把 8 步的产物声明为结构化 artifact，使每步可独立实现、可单测、可回放。

```text
DraftRequirement ──▶ [0] ──▶ RequirementSpec ──▶ [2] ──▶ ImpactAnalysis
      │                  │                            │
      │             ClarificationSession              │
      │                  │                            ▼
      │                  └──────────────┐      ┌─ [3] 方案生成
      ▼                                 └──────┴▶ RepoModificationPlan[]
[1] 需求解构 ────────────────────────────────────────────────▶ [4] 评审
                                                                      │
                                                                      ▼
                                                              [5] 执行 ──▶ ExecutionRun
                                                                              │
                                                                              ▼
                                                                      [6] 提交 ──▶ RepoCommit[]
                                                                              │
                                                                              ▼
                                                                      [7] 反馈 ──▶ 图增量 diff
```

**关键 artifact 骨架**

```text
DraftRequirement {
  text
  hint?          // 可选：目标仓提示、优先级、是否允许破坏性变更
}

ClarificationQuestion {          // [0] 追问的结构化表达
  id
  text
  kind           // select | multi-select | input | confirm
  options?       // [{ label, description?, recommended? }]
  default?
  blocking       // true=阻断级（必答），false=可默认跳过
  context        // 生成该问题的图谱依据（可回显给用户）
}
ClarificationSession { questions: ClarificationQuestion[]; answers?: Record<id, value> }

RequirementSpec {                // [0]+[1] 澄清+解构后的完整规格
  text                           // 原始需求 + 补充决策
  goals[]                        // 拆出的子目标
  candidateRepos[]               // 直接涉及仓（含图中不存在的新仓）
  constraints[]                  // 破坏性/兼容/时间等约束
  acceptance[]                   // 验收标准
}

ImpactAnalysis {                 // [2] 产物
  affectedRepos[]                // 候选仓 ∪ 反向可达波及仓
  topologicalOrder[]             // SCC 缩点后的执行顺序（原子单元为粒度）
  criticalEdges[]                // 高风险契约边 / 环（强制人审）
  conflicts[]                    // 写范围冲突清单
}

RepoModificationPlan[]           // [3] 产物，结构见 §5.3（每仓一份）

ExecutionRun {                   // [5]-[6] 运行态快照
  perRepo: { repo, sessionId, state, commit?, diffSummary? }
  errors[]                       // 失败/回滚/需人介入的项
}
```

**为什么先钉这套协议**：artifact 是管道各步骤之间的唯一接口——`[0]` 只负责产出 `RequirementSpec`，`[2]` 只消费 `RequirementSpec` 产出 `ImpactAnalysis`，互不越界；这也让「屏幕追问的 UI 绑定」「影响面计算的单测」「图谱反馈的 diff」各自都能独立落地和回放。

## 14. 分发与一键安装（Packaging & Distribution）

> 需求：其他用户一键安装。DSH 官方插件形态是**组合包（bundle）**，本插件按官方规范打包，目标「一条命令装好」。

### 14.1 交付形态：DSH 组合包 + 客户端 bundle

本插件一个包同时贡献两面（后端能力 + 前端 UI）：

- **Host 半**：`dsh.bundle` 声明 + `cordis.patch.yml`——注册 RepoGraph 服务、编排器、git 封装、追问/审批等后端插件。
- **Client 半**：`dsh.client` 声明 + `exports["./client"]` 导出**预构建**浏览器 bundle——看板 UI、图形化关系编辑器、追问交互。

```jsonc
// package.json（示意，字段以官方 manifest 为准）
{
  "name": "dsh-repo-board",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "exports": {
    ".": "./lib/index.js",
    "./client": "./lib/client.js"             // dsh.client 的浏览器 bundle
  },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },  // host 侧插件层
    "client": { "platform": "web" }                // client 侧注册
  },
  "peerDependencies": {
    "@deepseek-ai/cordis": "…",
    "@deepseek-ai/dsh-base": "…"
  }
}
```

### 14.2 三种分发渠道（一键安装的三种难度）

| 渠道 | 安装命令 | 是否真「一键」 | 说明 |
|---|---|---|---|
| **npm 发布（推荐）** | `dsh plugin add dsh-repo-board` | ✅ 是 | 预构建产物，零授权，一条命令 |
| **GitHub 安装** | `dsh plugin add github:yl6666/dsh_persional` | ⚠️ 需额外一步 | 拉源码，需 `prepare` 自包含构建 + 用户授权 `allowBuilds` |
| **tarball 交付** | `dsh plugin add ./dsh-repo-board-0.1.0.tgz` | ✅ 是 | 预构建，适合内网/离线 |

**结论**：正式发布走 **npm**（真正一键）；开发/尝鲜走 **GitHub + prepare**；内网走 tarball。

### 14.3 一键安装的用户旅程（目标体验）

```
1. 安装（一条命令）
   dsh plugin add dsh-repo-board
   （首次自动初始化 profile，追加到 dsh.profile.bundles）

2. 启动
   dsh --profile <name>
   （host 插件加载；client bundle 经 dsh.client 注入 Web GUI，看板自动出现）

3. 首次使用引导
   看板首次打开 → 引导「导入/新增一组仓库」→ 自动跑关系分析 → 生成图谱
```

### 14.4 打包工程要求（为「一键」扫清障碍）

- **预构建产物交付**：npm/tarball 携带 `lib/` 构建产物，用户**无需授权 `allowBuilds`**（这是 GitHub 渠道才有的坎）。
- **`prepare` 自包含**：若走 GitHub，`prepare` 必须不依赖旁边有 monorepo checkout（独立 tsdown 转译，不做类型检查）。
- **client bundle 预构建**：`exports["./client"]` 导出已构建的浏览器 bundle，而非源码。
- **peerDependencies 正确**：声明对 `@deepseek-ai/cordis`、`@deepseek-ai/dsh-base` 等的 peer 依赖；内置组合包从 dsh 安装目录解析，可放心依赖 agentTeams / subagents / workspace / client-modules。

### 14.5 运行时外部依赖（安装后还需配置）

本插件比普通插件多三类外部依赖，需在首次引导/config 中妥善处理：

- **git 凭据**：clone/push 需本机 SSH/credential manager，或插件配置里提供 token（§12 决策点 5）。
- **网络/代理**：访问远程仓库，复用 DSH 的网络代理配置。
- **LLM 语义标注**：semantic-annotator 消费 token，通过 config schema 暴露「仅静态 / 静态+语义」开关与模型选择（§12 决策点 2）。

### 14.6 版本与升级

- 语义化版本；图谱数据格式（§13.1）自带 `version` 字段，跨版本迁移。
- 升级 = `dsh plugin update dsh-repo-board`（pnpm 转发）；图谱是**项目级文件，不随插件版本走**，升级不丢图。
